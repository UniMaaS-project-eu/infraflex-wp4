# unimaas_infraflex

Integration layer connecting the Infraflex production line to the UniMaaS platform.

## Architecture

```
Physical device (robot, AMR, lift, …)
    │  MQTT  Infraflex/Executors/{path}/{Data|Status|Task}
    ▼
vo_layer/vo_manager.py          ← WoT Virtual Object per device (wotpy2)
    │  Kafka  infraflex.vo.property.updates  (batched every 3 s)
    ▼
kafka/aas_consumer.py           ← PATCH BaSyx REST API
    │  BaSyx REST  /submodels/{id}/submodel-elements/{idShort}/$value
    ▼
BaSyx AAS Repository (port 8081)
    │  polled by kg/infraflex2kg.py (3 s interval)
    │  AND queried directly by ontology bridge
    ▼
GraphDB Knowledge Graph (port 7200)
    (Cell, RobotArm, ExecutorDevice RDF individuals — live state + relationships)
```

The three services above (`vo_manager.py`, `aas_consumer.py`, `infraflex2kg.py`) run
continuously in the background. The ontology bridge (`aas_to_ontology.py`) is
a separate on-demand tool that snapshots the current state as a TTL file.

See `../docs/architecture/architecture.png` and `../docs/architecture/flow.png` for the visual overview.

## Prerequisites

All dependencies are in `requirements.txt` and already installed in the project venv.
**Always activate it before running any script:**

```bash
source ../.venv/bin/activate   # Linux/macOS / WSL
..\.venv\Scripts\activate      # Windows CMD/PowerShell
```

Verify the right Python is active:

```bash
which python   # should point to .venv/bin/python
```

## Setup (one-time)

### 1 — Start infrastructure (Docker)

From the repository root:

```bash
docker compose up -d --build
```

This starts:
- **BaSyx AAS Environment** (port 8081) — AAS repository + REST API
- **AAS Registry** (port 8082)
- **Submodel Registry** (port 8083)
- **MongoDB** (internal)
- **Mosquitto** MQTT broker (port 1883) — *local broker only; Infraflex uses its own at `infraflex-nuc11phi7.infraflex.lan:1883`*
- **Redpanda** Kafka-compatible broker (port 19092)
- **AAS Web UI** (port 3000)
- **`unimaas-infraflex`** — `vo_manager.py`, `aas_consumer.py`, and `infraflex2kg.py`

Wait until Redpanda is healthy:
```bash
docker compose ps redpanda
```

### 2 — Load AAS shells into BaSyx

BaSyx loads all JSON/AASX files placed in `basyx-setup/aas/` on startup.
Copy the generated AAS files for robot arms, tools, add-ons, cells, and executor devices:

```bash
cp AAS/arms/*.aasx        basyx-setup/aas/
cp AAS/tools/*.json       basyx-setup/aas/
cp AAS/addons/*.json      basyx-setup/aas/
cp AAS/cells/*.json       basyx-setup/aas/
cp AAS/executors/*.json   basyx-setup/aas/
docker compose restart aas-env
```

The **executor files** (`AAS/executors/`) are one AAS shell per Infraflex device (PowerAir,
Lift, Turntable, AMR, Warehouse, Debonder). Each contains a single `LiveData` submodel
whose elements are updated in real time by `aas_consumer.py`.
Shell IDs and submodel IDs must match the `aas_shell_id` / `aas_submodel_id` fields in
`config/devices.json` — they are generated by `ontology_bridge/generate_aas.py` so they
already match.

> **Note:** `AAS/reference/AAS-UniMaas/` contains sample characteristic AAS files used for ontology
> bridge testing only — they are not meant to be loaded into BaSyx as production shells.

### 3 — Configure infrastructure

Edit `config/devices.json` to match your setup:

- **`mqtt.host`** — Infraflex MQTT broker hostname
- **`kafka.bootstrap_servers`** — Redpanda address (default `localhost:19092`)

The `devices` list is optional. `vo_manager.py` auto-discovers any executor that publishes to
`Infraflex/Executors/#` — it creates the WoT ExposedThing and POSTs the AAS shell to BaSyx
automatically on first message. Devices already listed in `devices` are pre-registered at
startup with their explicit IDs (useful when you need non-standard AAS IDs or want the VO
ready before the first MQTT message arrives).

## Live pipeline (Docker or manual)

When you run `docker compose up -d --build` at the project root, the **`unimaas-infraflex`** container automatically starts all three long-running services (`vo_manager.py`, `aas_consumer.py`, and `infraflex2kg.py`) once `aas-env`, `graphdb`, and `redpanda` are healthy:

```bash
# View live logs from all three services in Docker
docker logs -f unimaas-infraflex
```

Alternatively, you can run them manually on the host in separate terminals:

### VO Manager — MQTT → WoT → Kafka

```bash
cd vo_layer
python vo_manager.py
```

1. Creates a W3C WoT `ExposedThing` per Infraflex executor.
2. Subscribes to `Infraflex/Executors/#` on the MQTT broker.
3. Parses `Data`, `Status`, and `Task` messages and updates VO properties immediately.
4. Batches changed properties and publishes them to Kafka topic
   `infraflex.vo.property.updates` every **3 seconds**.

> **Kafka backlog:** if the consumer was stopped while the producer ran, the consumer group
> may replay old messages on restart. Skip to the latest offset with:
> ```bash
> rpk group seek infraflex-aas-consumer --to end --topics infraflex.vo.property.updates
> ```

### AAS Consumer — Kafka → BaSyx

```bash
cd kafka
python aas_consumer.py
```

Reads from `infraflex.vo.property.updates` and PATCHes the corresponding
BaSyx submodel elements via REST.

### KG Synchroniser — BaSyx → GraphDB

```bash
cd kg
python infraflex2kg.py
```

Polls BaSyx every 3 s. For each Infraflex shell it finds:

| Shell kind | GraphDB entity | Key properties / predicates |
|---|---|---|
| Cell AAS | `infraflex:Cell` | `rdfs:label`; `infraflex:hasArm` → RobotArm |
| Robot arm AASX | `infraflex:RobotArm` | manufacturer, model, payload, reach, … |
| Executor AAS | `infraflex:ExecutorDevice` | executorType, cell, operationalState, position, batteryLevel, … |

Useful SPARQL queries once it's running (open GraphDB Workbench at http://localhost:7200):

```sparql
PREFIX infraflex: <https://w3id.org/fm/infraflex#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

# Full graph — see cells, mounted arms, and executors:
SELECT ?cell ?arm ?executor WHERE {
    ?c a infraflex:Cell ; rdfs:label ?cell .
    OPTIONAL { ?c infraflex:hasArm ?a . ?a rdfs:label ?arm }
    OPTIONAL { ?c infraflex:hasExecutor ?e . ?e rdfs:label ?executor }
}
ORDER BY ?cell

# Live operational state of all executors:
SELECT ?cell ?type ?state ?skill WHERE {
    ?c infraflex:hasExecutor ?e ; rdfs:label ?cell .
    ?e infraflex:executorType ?type .
    OPTIONAL { ?e infraflex:operationalState ?state }
    OPTIONAL { ?e infraflex:currentSkill ?skill }
}
ORDER BY ?cell ?type

# AMR position and battery state:
SELECT ?amr ?state ?battery ?skill WHERE {
    ?e a infraflex:AMRExecutor ; rdfs:label ?amr .
    OPTIONAL { ?e infraflex:operationalState ?state }
    OPTIONAL { ?e infraflex:batteryLevel ?battery }
    OPTIONAL { ?e infraflex:currentSkill ?skill }
}

# Live device telemetry and synchronization timestamps:
SELECT ?device ?type ?state ?skill ?lastSync WHERE {
    ?e a infraflex:ExecutorDevice ;
       rdfs:label ?device ;
       infraflex:executorType ?type .
    OPTIONAL { ?e infraflex:operationalState ?state }
    OPTIONAL { ?e infraflex:currentSkill ?skill }
    OPTIONAL { ?e infraflex:lastUpdated ?lastSync }
}
ORDER BY DESC(?lastSync)
```

Or query live GraphDB data directly from the terminal via SPARQL REST API:

```bash
curl -s -X POST http://localhost:7200/repositories/infraflex \
  -H "Accept: application/sparql-results+json" \
  --data-urlencode "query=PREFIX infraflex: <https://w3id.org/fm/infraflex#> SELECT ?device ?type ?state ?skill WHERE { ?e a infraflex:ExecutorDevice ; rdfs:label ?device ; infraflex:executorType ?type . OPTIONAL { ?e infraflex:operationalState ?state } OPTIONAL { ?e infraflex:currentSkill ?skill } }"
```

## Ontology bridge (on demand)

Run this whenever you want a fresh RDF snapshot of the production line state.
The source ontology definitions in `../ontologies/base/` are never modified.
Output is written to `../ontologies/instances/` (gitignored — local only).

```bash
cd ontology_bridge

# Normal use — runs both steps automatically
python aas_to_ontology.py

# If GraphDB is unavailable (still exports AAS structure + BaSyx live data)
python aas_to_ontology.py --skip-kg

# Override output location
python aas_to_ontology.py --output /tmp/my_export.ttl
```

**What the script does, in order:**

| Step | What it does |
|---|---|
| **1 — Enrich** | Reads `ontologies/base/infraflex-ontology/data/*.ttl` and pushes any property values defined there into the matching BaSyx AAS shells. This captures things the ontology knows that MQTT never sends — nominal values, defined capabilities, structural parameters. |
| **2 — Export** | Reads AASX files + AAS JSON + BaSyx (now enriched + live data) + GraphDB KG and writes `ontologies/instances/infraflex_instances.ttl`. |

Running enrich before export means the TTL snapshot always includes both live device state
and ontology-defined properties together.

**If you only need one step:**

```bash
# Push ontology-defined properties into BaSyx only (no TTL written)
python aas_to_ontology.py --only enrich

# Generate TTL snapshot only (skip the BaSyx enrichment)
python aas_to_ontology.py --only export
```

**Export sources (all combined into one TTL):**

| Source | What it contributes |
|---|---|
| `AAS/arms/*.aasx` | Robot arm specs (payload, reach, speed, …) |
| `AAS/tools/*.json`, `AAS/addons/*.json`, `AAS/cells/*.json` | Static tool / add-on / cell structure |
| `AAS/executors/*.json` | Executor shell type declarations (`LiftExecutor`, `PowerAirExecutor`, …) |
| BaSyx LiveData submodels (live REST query) | Current operational state per executor: `OperationalState`, `CurrentSkill`, `TaskState`, `GripperClose`, `Position`, `BatteryLevel`, … |
| GraphDB KG | Runtime relationships (cell↔arm, process↔resource, …) |

## File structure

```
Unimaas/
├── AAS/
│   ├── arms/                     # Robot arm AASX files (source, from kg_cognee)
│   ├── tools/                    # Tool AAS JSON templates (FingeredGripper, SuctionGripper, ScrewDriver)
│   ├── addons/                   # Add-on AAS JSON templates (Table, Lift, Conveyor)
│   ├── cells/                    # Cell AAS JSON instances (Cell1–Cell6, refs arm shells)
│   ├── executors/                # Executor AAS shells — one per device (13 files, generated)
│   │                             #   e.g. cell5_lift.json, amr_mir200_1.json, …
│   │                             #   Each has a LiveData submodel updated by aas_consumer.py
│   └── reference/                # Reference AAS datasets (AAS-UniMaas, AAS-RAASCEMAN)
│
├── ontologies/
│   ├── base/                     # Source ontology definitions — read-only, do not modify
│   │   └── infraflex-ontology/
│   │       ├── ontologies/       # resource-def.ttl, process-def.ttl, …
│   │       └── data/             # Instance data (resource-sampl1.ttl, …) — read by enrich step
│   ├── refined/
│   │   └── process-rec.ttl       # Refined process recording & executor ontology
│   └── instances/                # ← generated, gitignored
│       └── infraflex_instances.ttl # Latest Infraflex ontology export (AAS + live state)
│
└── unimaas_infraflex/
    ├── config/
    │   └── devices.json          # Infrastructure config (MQTT/Kafka/BaSyx/GraphDB/ontology)
    ├── vo_layer/
    │   ├── thing_descriptions.py # WoT TD templates per device type
    │   └── vo_manager.py         # MQTT→VO→Kafka bridge (3-second publish batching,
    │                             #   auto-discovers new devices via wildcard MQTT subscription)
    ├── kafka/
    │   └── aas_consumer.py       # Kafka→BaSyx REST updater
    ├── kg/
    │   ├── graphdb_client.py     # Ontotext GraphDB REST & SPARQL 1.1 client
    │   └── infraflex2kg.py       # BaSyx→GraphDB KG synchronizer (Cell/RobotArm/ExecutorDevice)
    └── ontology_bridge/
        ├── aas_to_ontology.py    # Ontology bridge (enrich BaSyx + export TTL, reads Infraflex KG)
        └── generate_aas.py       # Generator for tool/addon/cell/executor AAS files
```

## Adding a new device type

> Adding a new *instance* of an existing type (e.g. a second Lift in Cell4) requires no
> code changes — `vo_manager.py` will auto-discover it when it first appears on MQTT.
> The steps below are only needed when adding a brand-new *type* of executor.

1. Add a `_td()` builder function in `vo_layer/thing_descriptions.py`.
2. Register it in `DEVICE_TYPE_TO_TD`.
3. Add an extractor dict in `PROPERTY_EXTRACTORS` in `vo_manager.py`.
4. Add the device type and its `LIVEDATA_PROPERTIES` to `ontology_bridge/generate_aas.py`, then re-run `python generate_aas.py` to produce the executor AAS template file.
5. Add live property mappings to `EXECUTOR_PROP_MAP` and the class to `EXECUTOR_ONTO_CLASS` in `ontology_bridge/aas_to_ontology.py`.
6. Optionally add an entry to `config/devices.json` `devices` list if you need a non-standard AAS ID or want the VO pre-registered before the first MQTT message.
